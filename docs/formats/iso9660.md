# ISO 9660

Not a sampler filesystem. A meaningful share of these collections are libraries that were converted to Kontakt or to plain audio and burned back to a disc image — they mount on a modern machine, but they still arrive wrapped in a `.nrg` or a compressed `.mdx` that nothing else opens, so reading them here costs little.

The standard itself is well documented elsewhere and this file does not restate it. What it records is the part that cost real time: **which of a disc's two name spaces you must read**, and what happens when you read the wrong one.

## Two name spaces, one set of files

A disc may carry more than one volume descriptor, each with its own root directory, each describing *the same extents under different names*. Every descriptor sits in its own sector from sector 16 onward, ends the chain with a terminator, and carries `CD001` at offset 1.

| Offset | Size | Meaning |
|---|---|---|
| 0 | 1 | Descriptor type — 1 primary, 2 supplementary, 255 terminator |
| 1 | 5 | `CD001` |
| 40 | 32 | Volume identifier |
| 88 | 32 | Escape sequences (supplementary descriptors only) |
| 156 | 34 | The root directory record, inline |

A **supplementary descriptor whose escape sequences begin `%/@`, `%/C` or `%/E` is Joliet**: its names are UCS-2 big-endian, up to 64 characters, mixed case, spaces and all. The three sequences are UCS-2 levels 1, 2 and 3 and mean the same thing to a reader. *Verified: both ISO 9660 discs in the collection carry `%/E`.*

The **primary** descriptor's names are the ISO 9660 short names: uppercase, `;1`-suffixed, and — depending entirely on what mastered the disc — 8.3. They are what we read before, and they are lossy.

Anything else in a supplementary descriptor is not Joliet and must be ignored; reading it as UCS-2 would produce garbage names for the same files.

## The short names are not unique

This is the finding. **8.3 mangling is not injective, and at least one real disc relies on that.**

MagicISO v5.2 caps the whole short name at twelve characters — base, dot and extension together, rather than 8 + 3 — and when the `~N` collision counter runs into four digits it eats the extension rather than the base. `VINTA~397.EB` is well formed by that rule. `VINTA~1000.E` is what *every* index from 1000 upward becomes.

*Verified against `vintage-pro`:*

| | Primary tree | Joliet tree |
|---|---|---|
| Root directory extent | 19364 | 19365 |
| Files walked | 1062 | 1062 |
| Distinct paths | 1002 | 1062 |
| Files under `VINTAG~0.EXB/SAMPLE~0/VINTA~1000.E` | 61 | — |
| Volume identifier | `VintagePro\0` + `57` | `VintagePro` |
| Sample pool | `VINTAG~0.EXB/SAMPLE~0/` | `Vintage Pro.exb/SamplePool/` |

Sixty-one files, all different sizes, all one path. The count was never wrong — the walk always found all 1 062 — so a test that counts files passes throughout. Distinctness is the assertion that catches it.

`bsbssd2` shows the other half of the picture: its primary names are not 8.3 at all but relaxed Level 2 with embedded spaces (`BARI SRT   1.WAV`), they collide nowhere, and all 1 896 of its WAVs extract from either tree byte for byte. A disc can therefore look entirely healthy through the primary tree and still be one mastering tool away from the collision above. Preferring Joliet is not a fix for one disc; it is refusing to depend on the mastering tool's arithmetic ([ADR-0019](../adr/0019-prefer-joliet-names.md)).

## The volume identifier stops at the first NUL

The field is specified as space-padded. MagicISO NUL-terminates it and leaves whatever was in the buffer behind, so Vintage Pro's primary identifier reads `VintagePro\0` followed by `57` — a fragment of its volume set identifier `20101002_0257`, which is also where `MagicISO v5.2` signs the publisher and preparer fields. Reading past the NUL invented a volume named `VintagePro 57`, which is nowhere on the disc; the Joliet identifier says `VintagePro` and stops. *Verified against `vintage-pro`.*

## Rock Ridge

Neither disc carries it. Every directory record on both, in both trees, ends exactly at its name and its pad byte — zero system-use bytes to hold an `NM` entry. Joliet is what these discs actually use, and no Rock Ridge reader is needed to get long names off them. *Verified against `vintage-pro` and `bsbssd2`.*

## Appendix: the `.EBL` payload carries its own name

Not ISO 9660, and not read by anything yet — recorded here because it is the obvious next question about Vintage Pro's names, and because it corrects a plausible assumption. It belongs in an E-mu `EBL` document the day one exists.

Each `.EBL` is IFF: `FORM`, then form type `E5B0`, then a `TOC2` chunk of exactly 78 bytes, then `E5S1`. Twelve bytes into the `TOC2` data, at **file offset 34, is a 64-byte name field** — and it is **UCS-2 little-endian, not UTF-8**, holding at most 16 characters, space-padded, with the remaining 32 bytes zero. `909 Tom Low`, `Happy Hat`, `Snare 14`.

It is the best *display* name on the disc and a poor *unique* one: across Vintage Pro's 1 061 files it yields 1 057 distinct values. A converter should use it for the name a musician reads and must not rely on it for the path it writes. *Observed across all 1 061 files on `vintage-pro`; no test asserts it, because nothing parses `.EBL` yet.*
